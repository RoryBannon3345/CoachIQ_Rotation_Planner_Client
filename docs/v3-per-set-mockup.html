4 · Decisions this mockup is asking you to confirm

  • Tick lists become per-set. The game's single playerIds becomes one list per set. That is a state-model change, and it bumps the saved-session schema (2 → 3).
  • The 12-player cap is measured as the union across a game's sets, matching statsContract.ts's maskCount(union, …). What gets refused is ticking a 13th distinct girl into any set — not 13 in one set. The guide does not mention this; it follows the reference implementation.
  • Un-ticking is guarded per set. Today a girl with counts anywhere in the game cannot be un-ticked at all. Now she can be un-ticked from a set she has no counts in, and the refusal message names the set.
  • A merge never shrinks a set count below recorded data. If a re-sent roster says 2 sets but she has already recorded into set 4, the game keeps 4 tabs. mergeDayRoster is documented as non-destructive by construction; this keeps that true.
  • Existing saved days keep five tabs. A schema-2 save carries no set count, so migration gives it MAX_SETS and copies the old per-game list into every set. An in-progress day already on a phone looks and behaves exactly as it did.
  • Legacy CIQR1./CIQR2. emails normalise to one set holding that game's whole roster, via maskOf, exactly as the Planner's normaliseRosterV2 does. One tab — not three, not five.
